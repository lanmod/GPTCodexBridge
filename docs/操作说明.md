# WebCodexBridge 操作说明

这份说明面向日常使用：ChatGPT 负责思考和评审，Codex 负责本地执行，WebCodexBridge 负责把任务、Git、终端、浏览器和 GitHub 串成一个可审计、可回滚、可复用的闭环。

## 一、操作界面

推荐主界面是本地浏览器任务驾驶舱：

```bash
wcb serve --port 8787
```

打开终端输出里的本地地址后，在浏览器里看当前任务状态、任务流水线、下一步建议，以及给 Codex、ChatGPT、GitHub 的交接内容。

CLI 仍然保留，用来执行明确动作：

- 创建任务；
- 生成 Codex 执行提示；
- 生成 snapshot；
- 本地提交；
- 回滚；
- 生成 GitHub 交接包或发布 PR。

日常心智模型是：

```text
浏览器驾驶舱看状态
  -> CLI 执行动作
  -> Codex 修改代码
  -> ChatGPT 评审结果
  -> Git / GitHub 留下审计记录
```

## 二、首次准备

进入项目目录：

```bash
cd /Users/lanmod/Documents/WebCodexBridge
```

安装依赖并构建：

```bash
npm install
npm run build
```

如果希望直接使用 `wcb` 命令，可以执行：

```bash
npm link
```

初始化 Bridge：

```bash
wcb init
```

检查环境：

```bash
wcb doctor
```

医生检查里最重要的是两类状态：

- `本地 Git 闭环: 可用`：可以创建任务、提交、回滚、生成 snapshot。
- `GitHub 共享状态层: 可用`：可以 push 分支并创建 PR。

如果 GitHub CLI 或 `origin` remote 缺失，本地 Git 闭环仍然可以先用；GitHub 发布可以等后面再配置。

## 三、启动任务驾驶舱

启动本地控制台：

```bash
wcb serve --port 8787
```

浏览器打开：

```text
http://127.0.0.1:8787
```

如果 8787 被占用，可以换一个端口：

```bash
wcb serve --port 8881
```

页面里重点看四块：

- `当前阶段`：告诉你现在应该做什么。
- `任务流水线`：从创建任务到 GitHub 交接的 6 个步骤。
- `工作区`：判断本地是否有未提交改动。
- `交接内容`：复制给 Codex、ChatGPT 或 GitHub 的内容。

## 四、一次完整任务流程

### 1. 在 ChatGPT 里想清楚任务

先在 ChatGPT 里讨论需求、边界和验收方式。确认后，把任务标题和说明带回本地。

### 2. 创建本地任务和分支

```bash
wcb task create --title "修复登录错误" --description "用户登录失败时需要显示明确错误，并补充测试。" --checkout
```

这一步会记录任务信息，并切换到任务分支。

如果任务标题是中文，Bridge 会自动生成安全的英文分支名。

### 3. 生成给 Codex 的执行提示

```bash
wcb codex prompt --verify "npm test -- --run"
```

命令会生成：

```text
.webcodexbridge/tasks/<task-id>/codex-prompt.md
```

把这个文件里的内容交给 Codex 执行。Codex 应该只围绕当前任务改代码，不直接推送远端分支。

### 4. 让 Codex 执行

在 Codex 里修改代码、跑测试、修复问题。完成后不要急着提交，先生成结果包。

### 5. 生成 snapshot

```bash
wcb snapshot --verify "npm test -- --run"
```

snapshot 会包含：

- 任务标题和说明；
- 当前分支；
- Git 状态；
- diff stat；
- 完整 diff；
- 验证命令和输出。

这个 snapshot 是交给 ChatGPT 评审和 GitHub PR 使用的主要审计材料。

### 6. 交给 ChatGPT 评审

把 snapshot 的路径或内容发给 ChatGPT，并使用类似提示：

```text
请基于这个 snapshot 评审 Codex 修改是否合理，重点看风险点、遗漏测试、回滚风险，以及是否需要继续修改。
```

如果 ChatGPT 认为需要继续改，回到 Codex 执行，再重新生成 snapshot。

### 7. 本地提交

确认结果可接受后执行：

```bash
wcb commit
```

Bridge 会自动 stage 当前改动，并创建中文提交信息：

```text
任务提交：<任务标题>
```

### 8. 生成 GitHub 交接包

如果还不想直接发布 PR，先生成交接包：

```bash
wcb github package --base main
```

交接包会生成：

```text
.webcodexbridge/tasks/<task-id>/github-pr-package.md
```

里面包含 PR 标题、PR body 文件、push 命令、`gh pr create` 命令，以及给 ChatGPT 的 PR 评审提示。

### 9. 发布 GitHub PR

确认 `wcb doctor` 里 GitHub 共享状态层可用后，可以发布：

```bash
wcb github publish --base main
```

发布前需要满足：

- 当前任务已经有 snapshot；
- 本地代码改动已经提交或清理干净；
- 已配置 `origin` remote；
- 已安装并登录 GitHub CLI。

## 五、回滚任务

如果任务方向不对，需要回到任务开始前的 base commit：

```bash
wcb rollback --force
```

这会丢弃当前未提交代码改动，并把任务状态记录为已回滚。Bridge 会保留 `.webcodexbridge/` 下的任务元数据和 snapshot，方便审计。

执行回滚前建议先看一眼：

```bash
wcb status
git status --short
```

```bash

```

## 七、推荐协作规则

- 任务开始前先在 ChatGPT 里想清楚目标和验收。
- 本地执行交给 Codex，不在 ChatGPT 里手动猜本地状态。
- 每次重要修改后都生成 snapshot。
- 提交前让 ChatGPT 基于 snapshot 做一次评审。
- 需要共享状态时优先用 GitHub PR，而不是口头描述。
- 所有文档、交接说明和 Git 提交信息默认使用中文。

## 八、常见问题

### `wcb doctor` 显示 GitHub 不可用怎么办？

本地任务、snapshot、提交和回滚仍然可以使用。GitHub 发布需要补齐 GitHub CLI 和 `origin` remote 后再执行。

### 什么时候用 `github package`，什么时候用 `github publish`？

`github package` 只生成交接材料，不联网发布。适合先检查 PR 文案和命令。

`github publish` 会真正 push 分支并创建 PR。适合环境已经配置好、任务也已经提交干净的时候。

### snapshot 生成后又改了代码怎么办？

重新执行：

```bash
wcb snapshot --verify "npm test -- --run"
```

以最新 snapshot 作为 ChatGPT 评审和 GitHub PR 的依据。

### 是否必须使用浏览器驾驶舱？

不是必须。CLI 可以完整跑通流程。但浏览器驾驶舱更适合日常判断当前阶段、复制交接内容和查看下一步。
